# Рой v3: стигмергия — архитектура

Статус: строится. Режим движка `engine: swarm` (по умолчанию). Прежние режимы
`coordinator` (совет на каждом шаге) и `pipeline` (фиксированные фазы)
остаются для сравнения и старых прогонов.

## Почему не v2

v2 — комитет над работой: совет из двух+ моделей с голосованием на каждом
шаге. Задача на один вызов стоила 56 вызовов: ~38 — заседания, два
перепланирования из-за того, что ошибка среды (нет DNS) не считалась
ответом. В природе рой так не работает: нет собраний и начальника, каждый
действует сам, согласуясь через среду, и одну работу дважды не делают.

## Принципы → правила

| Природа | У нас |
|---|---|
| **Стигмергия**: муравьи общаются метками в среде | Среда — доска задач и файлы. У задачи метка: `needed`, `claimed`, `done`, `dead_end`, `waiting` (ждёт своих подзадач). Никаких собраний. |
| **Одну работу не делают дважды** | Задачу берёт один (метка `claimed`). Одинаковые задачи (по отпечатку цели) склеиваются: готовая — берётся её результат, взятая — новая ждёт её. |
| **Работа растёт только там, где нужно** | Агент берёт цель: может — делает и сдаёт; велика — сам раскладывает на 2–6 подзадач и вешает их. Простая задача = один агент. |
| **Разделение труда по порогам отклика** | У модели-семейства счёт успехов по типу работы (build, check, research, write, decide) из памяти. Для типа работы семейства с плохим счётом спрашиваются последними. Никаких раундов откликов. |
| **Метка «тупик» отпугивает** | Невозможно здесь (нет сети, нет доступа) → `dead_end` с причиной. Задачи с тем же отпечатком сразу тупик; причина — часть результата. Повторов нет. |
| **Кворум только при разногласии (пчёлы)** | Агент, собирающий подзадачи, видит противоречие → 3 независимые проверки разными семействами, решает большинство 2 из 3. Нет противоречий — коллектив ничего не стоит. |
| **Проверяет среда** | Код считается сделанным, когда агент запустил его (песочница) и запуск прошёл. Без запуска — задача возвращается «запусти»; вторая попытка без запуска принимается с пометкой «не проверено». |
| **Рой останавливается сам** | Цель `done` → конец. Решать «закончили ли» некому. |

## Поведение агента (одна задача)

Агент видит: свою цель, цепочку целей выше, что уже сделано на доске
(результаты и файлы), метки тупиков, результаты своих подзадач (если он
собирает), пометки прошлых попыток. Делает одно из:

1. `final` — сделал; для кода — после запуска и тестов, с реальным выводом.
2. `split` — задача явно больше одного агента: 2–6 подзадач с типом и
   `depends_on`. Нельзя дробить то, что можешь сделать сам.
3. `dead_end` — невозможно в этой среде; причина. Не повторять невозможное.
4. `conflict` — (собирая подзадачи) два результата противоречат; какие и в чём.

## Страховка (не способ работы)

- глубина дробления ≤ 3, подзадач у одной ≤ 6;
- попыток на задачу ≤ 3, потом `dead_end: gave up`;
- три шага подряд без единой смены метки — сдать лучшее, что есть;
- ожидание при сбоях моделей/роутера — как раньше.

## Цена

Задача «запусти код и скажи результат» — 1–3 вызова (шаги одного агента).
Большая задача — столько агентов, сколько подзадач, плюс сборка;
кворум — только на противоречиях.
