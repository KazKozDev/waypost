# Коллективный разум роя — план

Статус: этапы 1–2 готовы, этапы 3–7 впереди. Ветка: `fix/swarm-routing-failures` (или новая от неё).

## Где мы сейчас

Рой сейчас — конвейер с начальником: `supervisor → граф специалистов →
synthesizer → один reviewer → progress-monitor` (`waypost/swarm/engine.py`).
Каждое решение принимает один агент на одной модели. Агенты не видят работу
друг друга (кроме зависимостей), не спорят, не голосуют.

Что уже есть и на что опираемся:

- `waypost/families.py` — семейства моделей (`model_family`), роутер уже
  разводит план по семействам (`router.py:_diversify`).
- `waypost/ensemble.py` — `fanout_ensemble` (веер по разным семействам) и
  `self_consistency_sample`. Недостаток: веер берёт первый ответ без проверки.
- `output_schema` + проверка схемы в `verify.py` — роутер сам меняет модель,
  если ответ не по схеме.
- Предохранитель цикла: `AUTONOMOUS_REPLANS` / `AUTONOMOUS_FAILED_REVIEWS`.
- Локальная qwen3.8 — хвост каждой лестницы, но `concurrency: 1`.

## Сквозные правила (для всех этапов)

1. **Ширина коллектива адаптивная.** `SwarmConfig.collective_width`
   (по умолчанию 3). Если роутер отвечает отказами/429 или жив только
   локальный хвост — ширина падает до 1, рой работает как сейчас, а не
   падает. Безотказность важнее коллективности.
2. **Каждый этап — отдельный переключатель** в `SwarmConfig`
   (`diverse_models`, `review_panel`, `proposals`, `board`, `debate`,
   `memory`), по умолчанию включены. Можно выключить один, не ломая остальные.
3. **Никаких новых бесконечных циклов.** Каждый новый круг (критика, спор,
   голосование) — строго ограниченное число раундов; предохранитель цикла
   остаётся последним рубежом.
4. **Всё видно в живом логе** (`waypost/ui.py`): кто что предложил, как
   голосовали, что на доске.
5. **Тесты на каждый этап** на фейковом бэкенде (`tests/test_swarm.py`,
   `Scripted`), плюс прогон реальной задачи (тетрис) до и после — сравнить
   число вызовов, время, итог.
6. **Один этап — один коммит**, тесты зелёные перед коммитом.

## Этап 1 — Разные модели у агентов ✅

Сделано. Отличие от плана: семейство ответившей модели рой вычисляет сам
(`waypost.families.model_family` по `router.model`), поле в `RouterMeta`
не понадобилось. Попутно: `router.plan` получал `limit=4` по умолчанию, и
`ROUTER_MAX_ATTEMPTS` не удлинял лестницу — теперь сервер передаёт
`limit=settings.max_attempts`. Проверено вживую: три вопроса подряд ушли в
qwen (локальная) → gpt-oss (openai) → nemotron (llama).

Цель: участники коллектива думают по-разному, а не одна модель соглашается
сама с собой.

1. Роутер: расширение запроса `ChatRequest.avoid_families: list[str]`
   (как `output_schema` — вверх не отправляется). В `router.plan` кандидаты
   из этих семейств уходят в конец списка (не выкидываются — безотказность).
2. Роутер: в `RouterMeta` уже есть `model`; добавить `family` в ответ, чтобы
   рой знал, какое семейство ответило.
3. Рой: `WaypostLLM` принимает `avoid_families`; хелпер
   `engine._diverse_ask(role, n, ...)` делает n вызовов, передавая каждому
   следующему семейства уже ответивших.
4. Тест: три вызова одной роли получают три разных семейства; если доступно
   одно семейство — все три идут в него, без ошибки.

## Этап 2 — Комиссия проверяющих ✅

Сделано. Отличие от плана: аудит с инструментами (чтение файлов, запуск
кода) остаётся один — он собирает факты; вердикт по этим фактам выносит
панель из `collective_width` моделей разных семейств. Так разнообразие
мнений там, где модели расходятся, а квоты не утраиваются на инструментах.
Правила: большинство «прошло» → прошло; одно возражение не блокирует, а
пишется в замечания с пометкой «не подтверждено панелью»; при двух и более
возражениях сверщик (`review-consensus`) оставляет только замечания,
которые подняли ≥2 проверяющих, и план починки только под них.

Цель: убрать застревание на одном придирчивом проверяющем.

1. `review` фаза: вместо одного `reviewer` + `review-verdict` — панель из
   `collective_width` проверяющих на разных семействах (этап 1), параллельно.
2. Каждый возвращает `Review` (passed, findings, repair).
3. Агрегация (`engine._aggregate_reviews`):
   - прошло, если прошло у большинства;
   - замечание засчитывается, только если его подтвердили ≥2 проверяющих
     (сравнение замечаний — отдельный короткий вызов-«сверщик» по схеме, не
     строковое совпадение);
   - план починки берётся от проверяющего, чьи замечания совпали с
     подтверждёнными; при равенстве — отдельный вызов сводит планы.
4. Лог: вердикт каждого проверяющего и итог голосования.
5. Тесты: 2 из 3 «прошло» → completed; замечание одного → не блокирует;
   панель при ширине 1 = старое поведение.

## Этап 3 — Независимые варианты и выбор лучшего

Цель: ошибка одной модели не проходит в план и итог.

1. План: `collective_width` супервизоров на разных семействах параллельно
   составляют `Plan`, не видя друг друга.
2. Перекрёстная критика: каждый вариант получает короткий разбор от
   автора другого варианта (схема `Critique`: strengths, flaws, score).
3. Выбор: судья (отдельная роль `judge`, семейство не из авторов) получает
   варианты + критику и возвращает `Choice` (выбранный вариант или
   слияние). Для дискретного выбора — голосование авторов, судья решает
   ничью.
4. То же для итогового результата (`synthesize`): несколько сборщиков → выбор.
5. Роутер: `fanout_ensemble` — проверять ответы веера тем же `verify`, брать
   первый прошедший, а не первый пришедший (отдельный маленький фикс).
6. Тесты: плохой вариант отвергается судьёй; при одном доступном семействе
   — один вариант без критики.

## Этап 4 — Общая доска

Цель: параллельные агенты не делают одно и то же и не противоречат друг
другу.

1. `state["board"]`: записи `{kind: fact|decision|assumption|dead_end,
   text, author, round, id}`; хранится в чекпоинте, переживает resume.
2. Инструмент `board_post` в `waypost/swarm/tools.py` для специалистов;
   супервизор/монитор/судья пишут на доску свои решения автоматически.
3. Доска (последние N записей + все decision/dead_end) добавляется в
   `_context()` каждого агента.
4. Допущения, которые рой делает автономно (вместо вопроса пользователю),
   пишутся на доску как `assumption` — видны в итоге.
5. Тесты: запись одного агента видна в промпте другого; доска
   восстанавливается после resume; размер контекста ограничен.

## Этап 5 — Спор перед сборкой

Цель: противоречия между специалистами находятся до итога, а не на проверке.

1. Новая фаза `debate` между `execute` и `synthesize`, 1–2 раунда
   (`debate_rounds`, по умолчанию 1).
2. Каждый специалист видит результаты остальных и возвращает `Rebuttal`
   (contradictions, corrections); противоречия уходят на доску.
3. Если противоречий нет — фаза пропускается сразу (без лишних вызовов).
4. Сборщик получает результаты + противоречия и обязан их разрешить.
5. Тесты: противоречие попадает к сборщику; без противоречий — 0 лишних
   вызовов; число раундов не превышает лимит.

## Этап 6 — Память между запусками

Цель: рой не наступает на те же грабли в следующей задаче.

1. `var/swarm-memory.jsonl`: после каждого запуска — уроки: какие подходы
   провалились и почему (из замечаний проверки и `dead_end` с доски),
   какие роли на каких семействах прошли проверку.
2. Супервизор (этап 3) получает релевантные уроки в контекст; отбор по
   похожести задачи — через уже существующие эмбеддинги роутера
   (`waypost/embeddings.py`), если доступны, иначе последние N.
3. Статистика «роль → семейство → прошло проверку» подсказывает этапу 1,
   какие семейства предпочитать для роли (роутерный бандит учит модели,
   это — уровень подходов).
4. Тесты: урок из запуска A попадает в план запуска B; битая строка памяти
   не роняет рой.

## Этап 7 — Интерфейс

1. Вкладка «Рой»: варианты плана/итога и выбор судьи, голоса комиссии,
   доска (сворачиваемая панель), допущения.
2. Статус показывает текущую ширину коллектива и почему она сузилась
   (квоты / только локальная модель).

## Риски

- **Квоты.** Коллектив умножает вызовы в 2–4 раза; бесплатные тарифы
  ответят 429. Защита — адаптивная ширина (сквозное правило 1).
- **Локальная qwen одна и медленная** (`concurrency: 1`, ~20 с на ответ).
  В параллельных фазах она — один голос и запасной вариант, не основа.
- **Время.** Каждая коллективная фаза добавляет круг вызовов. Спор и
  критика ограничены раундами и пропускаются, когда нечего обсуждать.
