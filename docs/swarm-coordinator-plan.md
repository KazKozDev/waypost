# Рой v2: ведущий, доска с добровольцами, спор — план

Статус: этапы 1–6 готовы, этап 7 (живой прогон) впереди. Ветка: `fix/swarm-routing-failures`.

## Зачем

Рой v1 — конвейер из правил: фиксированные фазы «план → исполнение → спор →
сборка → проверка», фиксированные размеры коллектива и пороги. Агенты не
решают, как работать. На живом прогоне змейки 97 из 137 вызовов ушли на двух
сборщиков, которые час бились в правило «файл с таким именем уже есть» — ни
одно правило этого не поймало, а решать агентам было не дано.

## Что берём у других (см. обзор в чате)

- **Magentic-One (Microsoft):** ведущий ведёт *журнал задачи* (факты, догадки,
  план) и *журнал прогресса* (сделано ли, есть ли движение, не петля ли, кто
  следующий). Два шага без прогресса — пересмотр плана, а не продолжение.
- **Доска (bMAS, 2025):** ведущий вывешивает запросы, агенты сами решают,
  браться ли; +13–57% успешных задач против «начальник раздаёт».
- **Спор разных моделей (ReConcile, MAD):** независимые ответы → каждый видит
  чужие и пересматривает → до согласия. Модели склонны сдаваться большинству —
  побеждает довод, спор останавливается, когда мнения перестали меняться.
- **Оценка друг друга (DyLAN):** агенты оценивают вклад друг друга — это
  подсказка ведущему, кого звать.
- **Усилие по сложности (Anthropic):** простое — один агент, сравнение — 2–4,
  исследование — больше. Коллектив окупается только на развилках.
- **Почему такие системы падают (MAST, 1600+ прогонов):** на первом месте
  повтор уже сделанного (17%), на втором — «рассудил верно, сделал другое».
  Чинится устройством координации, не моделью побольше.

## Устройство

### Ведущий (координатор)

Отдельная роль. Держит в состоянии роя:

- `task_ledger`: задача, факты, догадки, план (открытые пункты), команда —
  роли, которые ведущий сам придумал под задачу.
- `progress_ledger`: запись на каждый его шаг — готово ли, есть ли прогресс,
  петля ли, что дальше и почему.

Каждый шаг ведущий смотрит на журналы и доску и выбирает **одно** действие:

| действие | что происходит |
|---|---|
| `post` | вывесить запросы на доску (что нужно, зачем, как проверить) |
| `deliberate` | вынести развилку на спор; ширину (1–5) выбирает сам |
| `review` | отдать результат комиссии; ширину выбирает сам |
| `finish` | собрать итог и сдать (после проверки, если она не пройдена — назад) |
| `replan` | переписать журнал задачи (план, команду) |

Тупик ловит **он сам**: в журнале прогресса поле «петля/нет движения». Два
таких шага подряд — движок заставляет `replan` (внешний цикл Magentic-One).

### Доска с добровольцами

- Запрос на доске: `id`, `need`, `why`, `done_when`, статус
  `open → claimed → done/failed`, кто взял, результат.
- **Отклик:** каждый член команды одним вызовом смотрит на открытые запросы и
  отвечает, какие может взять, с уверенностью и подходом. Запрос получает
  отклик с лучшим обоснованием (при равенстве — выше уверенность). Нет
  откликов — запрос возвращается ведущему с пометкой «никто не взял».
- Взявший работает инструментами (как специалист сейчас), результат и файлы
  ложатся на доску. Независимые запросы идут параллельно.

### Спор (развилки)

- Раунд 1: `width` моделей разных семейств независимо — позиция, довод,
  уверенность.
- Раунды 2–3: каждый видит чужие позиции и доводы, оставляет или меняет свою —
  и обязан сказать, какой довод его переубедил.
- Стоп: позиции перестали меняться или 3 раунда. Нет согласия — судья из
  другого семейства выбирает по **силе довода**, а не по числу голосов.
- Итог спора — решение на доске (`decision`), ведущий его видит.

### Что остаётся жёстким — только страховка

- лимит вызовов/времени (если задан), лимит раундов спора (3);
- два шага ведущего без прогресса → принудительный `replan`; три `replan`
  без прогресса → сдать лучшее, что есть, с перечнем нерешённого;
- ожидание при недоступности моделей/роутера (уже есть);
- исполнитель, который 6 шагов подряд не создал ни одного нового файла и не
  узнал ничего нового, останавливается и возвращает ведущему «застрял» —
  решает ведущий, а не правило.

### Что уходит

- Запрет «файл с таким именем уже есть в соседней папке» — превращается в
  подсказку в ответе инструмента, а не в отказ (то, что съело 97 вызовов).
- Фиксированные фазы v1 остаются как режим `engine: pipeline` для отката, по
  умолчанию — `coordinator`.

## Сделано и отличия от плана

- Код: `waypost/swarm/coordinator.py` (ведущий, доска, спор), схемы в
  `models.py`, режим `engine: coordinator` по умолчанию; `pipeline` — старые
  фазы, для прогонов, начатых до v2 (при «Продолжить» они остаются на фазах).
- **Отклик на запрос выбирается по уверенности**, а не по силе довода: оценка
  доводов — ещё вызов на каждый запрос. Довод-подход сохраняется у запроса и
  виден в журнале. Если это окажется слабым местом — добавить оценку.
- **Команда из одного человека не откликается** — ей запрос отдаётся сразу:
  спрашивать единственного исполнителя «возьмёшься?» — церемония.
- **Спор:** раунд 1 — независимые позиции; раунды 2–3 — каждый выбирает
  позицию с сильнейшим доводом и говорит, что его переубедило. Стоп — согласие
  или никто не сдвинулся. Нет согласия — судья из другого семейства по доводу.
- **Застрявший исполнитель:** 6 результатов инструментов подряд, которые он уже
  видел, — ход возвращается ведущему (`STUCK:`). Старый монитор повторов
  (3 одинаковых действия → перепланирование всего роя) в режиме ведущего
  выключен.
- **Сборка итога повторно не делается**, если готовые результаты не менялись.

## Этапы

1. **Ловушка записи и путаница ошибок.** Соседний файл — подсказка, а не
   отказ; «файл не найден» вместо «больше 2 МБ»; номера задач `r2:x` →
   `r2_x` до проверки схемы. Тест: два исполнителя пишут одно имя без петли.
2. **Журналы и шаг ведущего.** Схемы `TaskLedger`, `CoordinatorStep`; цикл
   ведущего вместо фаз; `replan` по двум шагам без прогресса. Тест: ведущий
   сам заканчивает простую задачу за минимум шагов.
3. **Доска с добровольцами.** Запросы, отклики, выбор по доводу, параллельное
   исполнение, «никто не взял». Тест: запрос уходит тому, кто лучше обосновал.
4. **Спор до согласия.** Раунды, «что переубедило», стоп по стабильности,
   судья по доводу. Тест: меньшинство с сильным доводом побеждает.
5. **Проверка и сдача.** `review` и `finish` через комиссию v1, провал — факты
   на доску и назад к ведущему. Застрявший исполнитель → ведущему.
6. **Интерфейс.** Журнал прогресса ведущего, запросы/отклики, раунды спора.
7. **Живой прогон** той же змейки: цель — десятки вызовов, а не 137, без
   петель.

После каждого этапа: тесты, пересборка, коммит.
