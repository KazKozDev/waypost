Architecture specification

Waypost

A local LLM-provider routing gateway that prioritizes free tiers and guarantees a local fallback

DocumentArchitecture requirements (SAD / SRS)
Version0.2 — accompanies the implementation
DateAugust 26, 2026
StatusCore implemented; the L1 classifier and the semantic cache (L2) are skeletons ready, trained on own telemetry. Hedging, idempotency, the Batch API, and the PII and guard layers are beyond the original scope
Target environmentA single Apple Silicon machine, one user
Key constraint Free-tier quotas, not a monetary budget

1Purpose and scope

Waypost is the single entry point for all LLM calls on the local machine. The client talks to an OpenAI-compatible endpoint and does not know which provider served the request; the system itself chooses the executor based on the request requirements, the remaining quotas, and the state of the providers.

The system's job is not "to pick the best model" but not to hit the quota. Free tiers are limited not by money but by the request rate and the token volume. It follows that the central object of the architecture is real-time accounting of remainders, not a model catalog. All other requirements are subordinate to this.

In scope

  • Routing of chat/completions calls between several providers and a local model
  • Quota accounting (requests per minute and per day, tokens per minute) that survives a process restart
  • Classification of the request by complexity and required capabilities
  • Response caching and support for provider prefix caching
  • Resilience: retries, a circuit breaker, a degradation ladder
  • Discovery and probing of available models
  • Telemetry as a training set for subsequent ML layers

Out of scope

  • Multi-tenancy, billing, user authorization — the system is built for a single owner
  • Horizontal scaling and distributed state
  • Model hosting and inference: the local runtime plugs in as a regular provider
  • Agent orchestration, a RAG pipeline, prompt management
Responsibility boundary Waypost decides where to send a request and does not interfere with its content. The only exception is the privacy filter, which forbids sending to the cloud but does not change the text.

2Context and actors

┌── control loop (background jobs) ──┐ │ discovery → probing → health │ │ ↓ write to registry │ └────────────────┬───────────────────┘ │ in-memory snapshot client → [ingress] → [cache] → [classifier] → [router] → [executor] → provider │ └→ local model
ActorRole and expectations
Client applications Code editors, scripts, agents. Expect full OpenAI compatibility: a base_url change without code edits.
Cloud providers Free tiers. Unreliable by definition: limits change without notice, availability is not guaranteed.
Local runtime A model on the owner's machine. No quotas, no network, private. The end point of the degradation ladder.
Owner Also the operator. Edits the manifest, reads the stats, runs probing. Has no on-call rotation — the system must recover on its own.

3Architectural drivers

Four constraints everything else is derived from. Requirements that follow from none of them should be considered redundant.

№Driver Architectural consequence
D1Quota scarcity Accounting for remainders is a mandatory participant in every routing decision, not an optional optimization. Quota state survives a restart: daily limits would otherwise be lost.
D2Data as payment A free tier is usually paid for with request content. The data policy is a filter, not a weight in scoring: a rule cannot be outweighed by quality or speed.
D3Cache vs routing conflict A provider's prefix cache only works when the same provider is hit with the same prefix. Smart routing inside a dialogue is guaranteed to zero it — hence the sticky session binding.
D4One machine, one process No distributed state. SQLite and in-memory structures instead of external stores; the absence of cross-node coordination simplifies both accounting and the cache.

4Functional requirements

Priorities: MUST — without this the system does not fulfill its purpose; SHOULD — substantially affects usefulness; COULD — an improvement on top of what works.

4.1 Facade and compatibility

IDRequirement Priority
FR-01 The system provides /v1/chat/completions, /v1/models endpoints compatible with OpenAI in request and response format. MUST
FR-02 The value model: "auto" hands the choice to the router. An explicitly named model bypasses scoring but keeps the degradation ladder. MUST
FR-03 Streaming is proxied without buffering the whole response. MUST
FR-04 The response contains a diagnostic block: the selected provider, the tier, the fallback path, the attempt count, the cache status. MUST
FR-05 Request extensions (privacy, latency_class, session_id, no_cache) are not forwarded to providers. MUST

4.2 Registry and discovery

IDRequirement Priority
FR-10 Providers and models are described by a declarative manifest; adding a provider requires no code change. MUST
FR-11 An offering without a declared key is excluded from the registry, not used with an auth error. MUST
FR-12 Probing measures the actual latency, the limits from the response headers, and the working (not declared) support for tool calling and JSON mode. SHOULD
FR-13 Discovery reconciles the provider catalog with the manifest and reports discrepancies. Automatic addition is forbidden: the catalog does not carry the license or the data policy. SHOULD
FR-14 Probing results override the manifest values without a restart. COULD

4.3 Quota accounting

IDRequirement Priority
FR-20 Each offering keeps independent buckets: requests per minute, requests per day, tokens per minute. MUST
FR-21 A "reserve before the call → reconcile after the answer" scheme: the preliminary token estimate is corrected by the actual spend. MUST
FR-22 A provider response about limit exhaustion blocks the offering for the time it specifies, even if the own counters show a remainder. The provider is trusted more than ourselves. MUST
FR-23 Bucket state is restored after a process restart. MUST
FR-24 Local offerings have no buckets and do not participate in accounting. MUST

4.4 Classification and selection

IDRequirement Priority
FR-30 The classifier determines the complexity tier, the task class, and the set of required capabilities; the result is a distribution with a confidence estimate, not a hard label. MUST
FR-31 Low confidence raises the tier. Underestimating complexity costs an escalation and double quota spend, overestimating costs only overspend; the asymmetry is baked into the thresholds. MUST
FR-32 Candidate selection consists of a hard filter and a subsequent scoring. Mixing the stages is forbidden: a capability weighed as a score allows picking a model that breaks the request. MUST
FR-33 The filter cuts by: context window, required capabilities, quota remainder, breaker state, data policy. MUST
FR-34 Scoring weights depend on the latency class: for background tasks speed barely matters, but saving the quota needed by interactive requests does. SHOULD
FR-35 The router returns an ordered plan of several candidates, not a single model. MUST
FR-36 The plan always includes a local offering, even if it lost the scoring. MUST
FR-37 Within a session, the binding to the chosen provider is kept while it is healthy and within quota. SHOULD
FR-38 The quality estimate of a model is refined from the accumulated telemetry, not left static. COULD

4.5 Caching

IDRequirement Priority
FR-40 An exact cache by the hash of the canonicalized request. Router extensions are not in the key: a session must not split the cache. MUST
FR-41 Only deterministic requests are cached. At a non-zero temperature the user asks for variety, and a repeated answer is a defect, not an optimization. MUST
FR-42 The prompt block order is stable and is not rearranged by the system: any permutation zeroes the provider's prefix cache entirely. MUST
FR-43 A semantic cache is allowed only with a cross-encoder confirmation of the candidate and a separation of spaces by system prompt, tool set, and language. COULD

4.6 Resilience

IDRequirement Priority
FR-50 Provider errors are normalized into a single set of verdicts: retry, switch, fatal, success. MUST
FR-51 A retry to the same provider is allowed only for server errors and timeouts, with exponential backoff and jitter. MUST
FR-52 Limit exhaustion switches to the next candidate without retries: a retry is guaranteed to get the same refusal. MUST
FR-53 An invalid request terminates immediately. Descending the plan will not fix an error in the request itself and only wastes quota. MUST
FR-54 A per-provider circuit breaker with states "closed — open — probe"; a repeated failure in the probe state doubles the pause up to a cap. MUST
FR-55 During streaming, a switch is possible only before the first byte sent to the client; after — the stream is honestly broken. MUST
FR-56 Plan exhaustion returns a structured error with the full path of attempts. MUST

4.7 Observability

IDRequirement Priority
FR-60 Every attempt is logged: the offering, the task class, the tier, the classification source, the verdict, the latency, the tokens. MUST
FR-61 The classification source is written mandatorily — otherwise it is impossible to tell whether the ML model improved routing or merely complicated the system. MUST
FR-62 A stats endpoint returns quota remainders, breaker states, the cache hit rate, and a daily summary. SHOULD
FR-63 Measured reliability is fed back into the registry and participates in scoring. SHOULD

5Non-functional requirements

The numeric values are acceptance targets, not guarantees. Each must be measurable by the existing telemetry.

IDAttribute Requirement and verification
NFR-01Overhead The system's own latency (without the provider time) is no more than 15 ms in the median with the ML classifier off. Verified by comparing the total latency and the attempt latency.
NFR-02Classification latency The deterministic level — fractions of a millisecond. The embedding level — no more than 5 ms. A heavy encoder is called for no more than 15 % of requests.
NFR-03Availability A failure of all cloud providers does not cause a system failure: the request is served by the local model. Verified by an integration test with unavailable upstreams.
NFR-04Restart resilience Daily quotas and the cache persist. Cold start — no more than 3 seconds until ready to accept requests.
NFR-05Accounting accuracy The share of limit-exhaustion responses is less than 2 % of all attempts with correct probing. An excess means a divergence of the manifest from reality.
NFR-06Extensibility Adding an OpenAI-compatible provider is a manifest edit, zero lines of code. Adding a provider with a different protocol is one new adapter with no change to the router and the executor.
NFR-07Resources The base mode needs no external services: no broker, no separate DB, no vector store. ML layers install optionally.
NFR-08Security Listening on the loopback or a private network interface, not all addresses. Provider keys never leave the machine and never enter logs or telemetry.
NFR-09Privacy A request in strict privacy mode cannot be sent to a data-training provider under any scoring state. Verified by a separate test.
NFR-10Testability Provider behavior is stubbed at the transport level; integration checks of the degradation ladder run without the network.

7Key architectural decisions

AR-01 · The facade mirrors OpenAI, not a custom protocol

Context
Clients are already written for an existing standard.
Decision
Full format compatibility; extensions are extra fields stripped before sending to the provider.
Alternative
A custom protocol — rejected: requires rewriting every client for zero benefit.
Consequence
The system is bounded by the expressiveness of a foreign format; provider-specific features are unavailable without extensions.

AR-02 · Quota accounting is primary to scoring

Context
Driver D1: the system's limit is rate and volume, not cost.
Decision
The quota remainder enters the hard filter, and the share of the daily limit enters scoring with a weight that depends on the latency class.
Consequence
The objectively better model may be refused to preserve the quota. This is intentional, not a defect.

AR-03 · The data policy is a filter, not a weight

Context
Driver D2: a free tier is paid for with request content.
Decision
The default for cloud providers is "trains on data"; an error this way is safe. Strict privacy mode cuts such providers before scoring.
Consequence
Strict mode in practice means the local model with all its quality limitations.

AR-04 · The local model is the end of the cascade, not an emergency mode

Context
The owner's machine can run a mid-size model at an acceptable speed.
Decision
The local offering is always in the plan, regardless of the scoring result.
Consequence
The system works without a single provider key. A cloud failure degrades quality but not availability.

AR-05 · Classification starts with rules, not a model

Context
Some features are read from the request fields and need no inference; there is no training data at the start.
Decision
The deterministic level is mandatory; ML levels plug in via a flag and train on own telemetry.
Alternative
A ready-made complexity classifier in the hot path — rejected: trained mostly on English, degrades on mixed traffic, does not fit the latency budget.
Consequence
For the first weeks routing runs on heuristics; this is a normal state, not incompleteness.

AR-06 · One store, and it is embedded

Context
Driver D4: one process, one user.
Decision
An embedded DB with journaling for quotas, the cache, and telemetry; in-memory structures for the hot path.
Alternative
An external counter store — rejected: in-process atomicity is enough, and the operating cost is non-zero.
Consequence
A second process instance would diverge the accounting. Runs strictly in one instance.

8The degradation ladder

The order is strict. A move to the next step is possible only after the previous one is exhausted.

StepAction Condition of application
1Retry to the same provider Only a server error or a timeout. A bounded number of attempts, backoff with jitter.
2Another key of the same provider When several keys are available. Not applied on an auth error.
3Another provider, same model Relevant for open-weight models hosted at several providers.
4Another model of the same tier The next candidate of the plan.
5A local model Always available. Quotas and the network do not participate.
6An approximate answer from the semantic cache Only with enable_degraded_cache: an L2 hit with a lowered threshold and an approximate: true marker. Serving it as fresh is not allowed. Available only before the first byte sent to the client.
7A structured error With the full path of attempts and the last refusal reason.
Streaming limitation Steps 1–6 are available only before the first byte sent to the client. After it, the stream belongs to the chosen provider, and the only correct behavior on a break is to honestly report the break, not to swap the source mid-answer.

10Risks and open questions

RiskManifestation and mitigation
Manifest divergence from reality Free-tier limits change without notice. Mitigation: regular probing, trusting the response headers above the own counters, a limit-refusal share metric as a staleness indicator.
False hits of the semantic cache Vector-close but opposite-meaning requests. The level is not enabled without a confirming encoder and a threshold tuned on own data. A threshold from an external source does not apply.
Prefix cache devaluation Switching providers inside a dialogue zeroes the warmed prefix. Mitigation: sticky binding and a ban on prompt block rearrangement.
Data leakage into free tiers Relying on the request author's attentiveness is unreliable. An automatic switch to strict mode on detecting personal data is planned.
Complexity without a gain ML layers are more interesting than the basic ones, which distorts priorities. Mitigation: the classification source in the log and a requirement of an end-to-end comparison with the heuristics before fixing the model.
A single instance A second process would diverge the quota accounting. An explicit launch lock is required, or a move to an external counter if multi-process becomes needed.

Open questions

  1. The threshold at which a cascade with escalation is better than a direct call to a strong model. Determined by measuring the failure share on the cheap tier, not by a general guess.
  2. The usefulness of a parallel duplicate request when the expected latency is exceeded: a tail-latency win against doubling the quota spend.
  3. The scope of context compression: token savings against accuracy loss and the destruction of the prefix cache.
  4. How to get labels for training the classifier on mixed bilingual traffic.
