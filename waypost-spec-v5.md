**Что изменилось относительно v4:**

### 0.1. Результат эксперимента с MTP — отклонено

Спекулятивный MTP-декодинг (`qwen-mtp-server.py` поверх Swift-воркера)
собран и запущен, сервер отвечает на `/v1`. **Ускорения на этой машине не
даёт.**

Причина: модель 27B в 4 битах занимает ~15 ГБ из 32 ГБ. Плюс система,
кэш Metal и отдельный фоновый процесс воркера. Свободной памяти не
остаётся, и параллельная верификация задрафтованных токенов съедает
больше, чем экономит. Рекордные показатели лидеров получены на 64–128 ГБ.

**Решение: MTP не использовать.** Локальный бэкенд — стандартный
`mlx_lm.server`: меньше памяти, нет второго процесса, стабильная скорость
без накладных расходов.

Репозиторий челленджа оставить как есть — не удалять, но и не подключать
к роутеру. Если машина когда-нибудь сменится на 64+ ГБ, вернуться к
замеру.

### 0.2. Бюджет памяти — пересчитан

Это самое важное следствие. Ориентировочно:

| Потребитель | Память |
|---|---|
| Qwen 27B 4-bit | ~15 ГБ |
| Система и приложения | ~6–8 ГБ |
| KV-кэш на длинном контексте | несколько ГБ |
| potion-multilingual-128M | ~0.3 ГБ |
| **Свободно** | **очень мало** |

Отсюда три жёстких вывода:

1. **`set_memory_limit(2**35)` (32 ГБ) из CLI-скрипта переносить нельзя** —
   это вся память машины. Значение годилось, когда модель была одна.
   Ставить ~22–24 ГБ (`22 * 2**30`), чтобы аллокатор упирался в лимит
   раньше, чем система начнёт свопить.
2. **`set_cache_limit(2**33)` (8 ГБ) снизить до ~4 ГБ.** Кэш-пул полезен,
   но на 32 ГБ он конкурирует с KV-кэшем.
3. **Gemma 4 12B резидентно рядом с 27B невозможна** (15 + 6.7 + система
   не помещаются). Локальная мультимодальность — только с выгрузкой
   основной модели, что дорого. См. раздел I.

Все значения вынести в переменные лаунчера, не хардкодить.

2. **Самый быстрый локальный путь работает мимо роутера.** В Waypost

6. **Память — связывающее ограничение**, а не скорость.

## A. Загрузить эмбеддинги

`embeddings: not loaded` блокирует **две** вещи. Помимо неготовности L1
это объясняет `semantic cache: 0.0%` — кэш без векторов не работает.
Загрузка `potion-multilingual-128M` включает оба пути, причём кэш даёт
эффект немедленно, без обучения головы.

- Загружать при старте, не лениво.
- `semantic_cache.similarity_threshold` в конфиг, старт 0.95, снижать по
  факту.
- Попадания в кэш логировать как `routing_source=cache`, чтобы они не
  попали в обучающую выборку как «успешный вызов модели».
- `compression: off` включать **после** эмбеддингов и отдельным
  изменением, иначе эффекты смешаются в метриках.
- Учесть ~0.3 ГБ в бюджете памяти (0.2).

## B. Персистить исходы

**Самое важное изменение во всём документе.**

Логика определения провала уже работает — `degenerate`,
`language_mismatch`, `empty`. Не хватает записи. Прошедшие запросы
разметки не оставили.

### B.1. Строка на попытку, не на запрос

```
attempt_log:
  request_id: uuid
  attempt_no: int
  ts: timestamp

  # вход
  embedding: float[256]           # potion; сохранять сразу — пересчитать
                                  # другим эмбеддером потом нельзя
  embedder_version: str
  l0_labels: {task_type, tier, complexity, lang, requires[]}
  l1_prediction: json | null      # писать даже когда не исполняется
  input_tokens: int
  modality: enum(text|image|audio|video|mixed)
  image_count: int
  audio_duration_s: float
  vision_token_budget: int | null

  # решение
  provider: str
  backend: enum(cloud|ollama|mlx|lmstudio|llamacpp)
  model: str
  model_version: str
  tier: enum(S|M|L)
  thinking_mode: bool
  routing_source: enum(l0|l1|cache|explore|forced|fallback|
                       escalation_thinking|escalation_cloud|hedge)
  is_exploration: bool
  quota_remaining_pct: float
  quota_window_reset_in_s: int
  quota_binding_limit: enum(requests|tokens)

  # результат
  status: enum(ok|timeout|rate_limited|error|refused|truncated)
  error_class: str
  latency_ms: int
  ttft_ms: int
  output_tokens: int
  reasoning_tokens: int | null
  peak_memory_mb: int | null      # для локальных вызовов

  outcome: enum(pass|fail|unknown)
  outcome_source: enum(hard_check|user_signal|judge|manual)
  outcome_detail: json
```

`peak_memory_mb` добавлено намеренно: на 32 ГБ память — связывающее
ограничение, и деградацию нужно уметь связать с ней, а не списать на
«модель медленная».

### B.2. Маппинг существующих детекторов

| Событие | outcome | source | detail |
|---|---|---|---|
| `degenerate` | fail | hard_check | `{reason: degenerate}` |
| `language_mismatch` | fail | hard_check | `{reason: language_mismatch, expected, got}` |
| `empty` | fail | hard_check | `{reason: empty}` |
| ответ отдан без эскалации | pass (слабый) | hard_check | `{weak: true}` |
| timeout / rate_limit | fail | hard_check | `{reason: <status>}` |

Слабый `pass` помечать явно: отсутствие срабатывания детектора не равно
правильному ответу. При обучении взвешивать ниже.

### B.3. Добить проверки уровня A

- код: синтаксический разбор, где возможно — запуск;
- JSON: парсинг и валидация по запрошенной схеме;
- обрыв по лимиту токенов → `truncated`, отдельно от `empty`;
- соблюдён ли запрошенный формат.

### B.4. Exploration — обязательно

Роутер всегда исполняет собственное решение → в логах исходы только
выбранной модели → данные отравлены собственной политикой, обучить
корректный предиктор невозможно.

- 5–10% запросов дублировать во **вторую** модель, случайную среди
  допустимых. Пользователю — только основной ответ, в лог — оба.
  `is_exploration=true`.
- Раз в N запросов игнорировать решение роутера полностью.
- Доля в конфиг: старт 10%, floor 2%.

При 66 моделях без exploration большая часть каталога никогда не получит
статистики.

### B.5. Ночной судья

Локальная модель проставляет `outcome` там, где жёсткие проверки не
сработали. Три оси: отвечает ли на вопрос; есть ли внутренние
противоречия; есть ли непроверяемые фактические утверждения. Пакетно,
ночью, `outcome_source=judge`. Здесь уместен thinking — латентность не
важна.

Запрещено спрашивать у модели-исполнителя её собственную уверенность.

## C. MLX-бэкенд

### C.1. Точка входа

`python -m mlx_lm.server` **устарел**. Корректно:

```bash
python3 -m mlx_lm server --model <MODEL_PATH> --host 127.0.0.1 --port 8000
# либо
mlx_lm.server --model <MODEL_PATH> --host 127.0.0.1 --port 8000
```

Эндпоинты: `/v1/models`, `/v1/chat/completions`. Порт 8000 — тот, который
MLX-бэкенд Waypost уже ожидает.

### C.2. Память

Сервер сам выставляет wired limit при старте:

```python
if mx.metal.is_available():
    mx.set_wired_limit(mx.device_info()["max_recommended_working_set_size"])
```

`set_cache_limit` он не трогает — переносить из CLI, но **с новыми
значениями** (см. 0.2): cache ~4 ГБ, memory ~22–24 ГБ. Значения из
CLI-скрипта (8 ГБ / 32 ГБ) на машине с соседями приведут к свопу.

### C.3. Thinking — НЕ фиксировать на сервере

`mlx_lm.server` поддерживает
`--chat-template-args '{"enable_thinking":false}'`.
**Не использовать.** Фиксация режима при старте убивает ступень
эскалации D.1.3 — вторую бесплатную по квоте попытку на том же весе.
Сервер поднимается в дефолте, режим передаётся per-request; решение
принимает роутер.

### C.4. Готовность к приёму запросов

При наличии `--model` веса грузятся при старте, но **HTTP-порт слушает
почти сразу, а 27B грузится 5–15 с**. Запрос в это окно подвиснет;
health-probe может счесть модель мёртвой.

Решение: отдельный `mlx-warmup` вторым LaunchAgent — опрашивает
`/v1/models` до успеха, затем один короткий запрос к
`/v1/chat/completions`. В основной лаунчер вставить нельзя: он
заканчивается `exec`.

### C.5. Артефакты

**`/Users/artemk/bin/mlx-server`** (chmod +x):

```bash
#!/bin/bash
set -e
PYTHON="/Users/artemk/mlx-env/bin/python"
MODEL="/path/to/EigenLabs/Qwen3.8-27B-4bit"
PORT=8000

exec "$PYTHON" -c "

try:
    mx.set_cache_limit($CACHE_LIMIT_GB * 2**30)
    mx.set_memory_limit($MEMORY_LIMIT_GB * 2**30)
except Exception:
    pass
import sys
from mlx_lm.server import main
sys.argv = [
    'mlx_lm.server',
    '--model', '$MODEL',
    '--host', '127.0.0.1',

```

`--chat-template-args` намеренно отсутствует (C.3).

`launchctl load ~/Library/LaunchAgents/ai.waypost.mlx.plist`

### C.6. Окружение: venv, не uv run

`uv run` при каждом рестарте разрешает окружение; без сети старт может
упасть. Для демона — постоянный venv (`/Users/artemk/mlx-env`), запуск
напрямую. launchd не наследует пользовательский `PATH` — все пути
абсолютные. При молчаливом незапуске смотреть `.err`.

CLI `~/bin/qwen-chat` можно оставить на `uv run`.

### C.7. Health-probe

Probe для MLX по тому же контракту, что у Ollama. Учесть окно прогрева
(C.4): probe до готовности не переводит модель в `dead`.

### C.8. Замер MLX против Ollama

**Замер «до» сделать на текущем CLI, прежде чем что-либо переносить.**

- одинаковый набор промптов на обоих бэкендах;
- метрики: TTFT, tokens/s, **пиковое потребление памяти** (на 32 ГБ это
  такой же критерий, как скорость);
- **обязательно на длинном контексте** — на коротких бэкенды идут
  вровень, разница вылезает там, где KV-кэш большой.

По результату: если MLX выигрывает — Qwen3.8 через MLX становится
локальным Tier L, Ollama остаётся под мелкую модель Tier S. Оба варианта
в конфиге с возможностью переключения.

## D. Local-first черновик и ступень thinking

### D.1. Цепочка эскалации

```
1. Локальная модель, thinking OFF → черновик.
2. Проверки уровня A (существующие + B.3).
   Прошёл → отдать. Квота не потрачена.
3. Не прошёл → та же локальная модель, thinking ON.
   Прошёл → отдать. Квота по-прежнему не потрачена.
4. Не прошёл → облако по обычной логике роутера.
```

**Обе локальные ступени не тратят облачную квоту вообще.**

### D.2. Настройки

- `local_first.enabled`, `local_first.thinking_escalation.enabled`.
- `local_first.thinking_timeout_ms` — ограничить и падать в облако по
  таймауту.
- Пропускать ступень 3 для типов задач, где рассуждение не помогает
  (перевод, извлечение, форматирование) — по `task_type`.
- Ступень логировать через `routing_source` и `thinking_mode`.

### D.3. Правила

- Локальную модель **не ставить в fan-out**: локальные вызовы
  последовательны, три вызова = тройное время.
- Служебный слой целиком локальный: эмбеддер, классификатор, судья,
  сжатие, извлечение полей.
- `qwen3:4b-instruct` (250 мс) — кандидат на нулевую ступень для
  тривиальных запросов. После базового варианта и только если данные
  покажут заметную долю запросов, которые 4b закрывает.

### D.4. Выбор резидентной модели — пересмотреть под 32 ГБ

27B занимает ~15 ГБ из 32 ГБ. Это почти половина машины и оставляет мало
места под KV-кэш и соседей. **Проверить гипотезу, что модель меньшего
размера окажется выгоднее.**

Критерий — не точность, а **сколько облачных вызовов модель экономит в
единицу времени**. Модель на 12–14B, проходящая проверку в 70% случаев
быстро и оставляющая память свободной, может обойти 27B с 80%, которая
свопит на длинных запросах.

Скрипт сравнения кандидатов (из числа `routable: false`): прогон
эвал-сета, метрики — доля прохождения проверок уровня A, TTFT **на
длинном контексте**, пиковая память. Результат зафиксировать в конфиге.

4 бита — нижняя граница; ниже деградация резкая, а не плавная.

## E. Сузить локальный пул

Ollama держит 9 загруженных моделей. При переключении веса выгружаются и
подгружаются; латентность прыгает и осядет в логах как «модель
медленная». На 32 ГБ это ещё и провоцирует своп.

- В маршрутизируемом пуле **две**: резидентная Tier L (по результатам
  C.8 и D.4) и `qwen3:4b-instruct` как Tier S.
- Остальные — `routable: false`, кандидаты для оффлайн-сравнения.
- Keep-alive так, чтобы резидентная не выгружалась.

## H. Замер β

150–200 запросов с известными ответами, репрезентативных для трафика.
Прогнать через все routable-модели. Посчитать:

- `p_best` — точность лучшей одиночной модели;
- `beta` — доля запросов, на которых ошиблись **все**;
- матрицу «кто с кем ошибается на одних и тех же запросах».

`1 - beta` — жёсткий потолок для любой схемы, выдающей ответ одного из
участников пула.

**Если `1 - beta - p_best` мал — фазу L не делать вообще.**

Локальную модель прогнать в обоих режимах (thinking on / off) как две
отдельные записи — покажет, окупается ли ступень D.1.3.

Побочный продукт — размеченный флаг «все ошиблись»: обучающая выборка
для `risk`-головы (J).

## I. Модальность как жёсткий пре-фильтр

Модальность — ограничение, а не предпочтение. Фильтр выполняется **до**
выбора тира. Детект — по структуре сообщения (блоки image/audio), не
классификатором: `potion` картинку не увидит.

### I.1. Матрица возможностей

```
model_capabilities:
  <provider>/<model>:
    vision: bool
    audio: bool
    video: bool
    max_images: int
    max_audio_seconds: int
    vision_token_budgets: int[]
    supports_tools: bool
    supports_json_schema: bool
    supports_thinking: bool
    max_context: int
    routable: bool
```

### I.2. Особенности Gemma 4 (в пуле 26b-a4b и 31b)

- Аудио поддерживается на E2B, E4B и 12B; на **26B A4B и 31B — нет**.
  Обе имеющиеся в пуле аудио не принимают, несмотря на caps `vision`.
  Аудио гонит вниз по размеру модели, против логики тиров; `audio + tier L`
  невозможно и решается декомпозицией.
- Аудио ≤30 с, видео ≈60 с (60 кадров при 1 fps). Спецификация, не
  настройка. Длиннее — конвейер с нарезкой.
- Бюджет визуальных токенов: 70 / 140 / 280 / 560 / 1120. Разница в
  расходе ~шестнадцатикратная. Роутер выставляет явно, дефолт не
  использовать.

| Задача | Бюджет |
|---|---|
| классификация, короткая подпись | 70–140 |
| описание сцены, вопрос по картинке | 280 |
| чтение крупного текста, схемы, графика | 560 |
| OCR плотного документа, таблицы | 1120 |
| покадровый разбор видео | 70 |

### I.3. Декомпозиция вместо маршрутизации

1. Дешёвая стадия превращает нетекстовый вход в текст (OCR / описание /
   расшифровка).
2. Текст идёт через обычный роутер **со всем пулом из 56 бесплатных
   моделей**.

Исключение — вопрос неотделим от изображения («что не так на этой схеме»).
Признак: дейктическая отсылка к изображению. При неуверенности —
декомпозиция.

### I.4. Локальная мультимодальность — отложить

**На 32 ГБ Gemma 4 12B резидентно рядом с 27B не помещается** (15 + 6.7 +
система). Варианты, в порядке предпочтения:

1. **Облачный вижн** (основной путь) — в пуле есть gemma-4-26b-a4b,
   gemma-4-31b, minimax-m3 с caps `vision`. Квоты узкие, поэтому
   декомпозиция (I.3) обязательна.
2. **Локальный вижн с выгрузкой** резидентной модели — только как фолбэк
   при исчерпании облачных вижн-квот. Дорого: выгрузка + загрузка +
   обратно. Реализовывать последним и с явным флагом в конфиге.
3. Резидентная Gemma — только если D.4 покажет, что основной моделью
   выгоднее взять что-то на 12–14B; тогда обе помещаются.

### I.5. Проверка OCR

Прогнать двумя моделями, сравнить нормализованные строки; расхождение
выше порога → `fail`. Сигнал уровня A без судьи.

Метки OCR-провалов — **отдельным классом**: испорченный вход для всей
цепочки, а не ошибка рассуждения.

## J. Голова, обученная на исходах

Требует данных из B (ориентир — от 5000 записей с `outcome`).

### J.1. Критическая ловушка

`scripts/train_head.py` **не должен** использовать метки L0 как целевую
переменную. Это дистилляция собственных эвристик: та же точность, но
медленнее. Целевая переменная — фактический `outcome`.

### J.2. Несколько голов на одном векторе

Один прогон `potion`, несколько независимых голов.

| Голова | Выход | Обучается на |
|---|---|---|
| `task_type` | категория | исходы, не метки L0 |
| `difficulty` | скаляр | исходы |
| `risk` | вероятность | флаг «все ошиблись» из H |
| `local_sufficient` | вероятность | закрылся ли запрос локально |

**`risk` — ключевая голова, которой нет.** «Сложно» и «весь пул сыпется» —
разные вещи. `risk` служит триггером для L.

`local_sufficient` обучается на данных D и позволяет пропускать локальный
черновик там, где он заведомо не поможет.

Длину контекста считать токенайзером, не предсказывать.

### J.3. Ограничение носителя

`potion` — статические эмбеддинги: порядок слов и контекст не
учитываются. Для темы, языка и типа задачи достаточно; для `difficulty` и
`risk` потолок ниже. Если качество слабое — настоящий энкодер **только для
них**. Не ставить несколько энкодеров в основной путь: бюджет латентности
роутера — десятки миллисекунд. Учитывать память (0.2).

### J.4. Ввод в строй

Голова работает **параллельно** с L0, решения пишутся в `l1_prediction`,
но не исполняются. Оффлайн-сравнение на отложенной выборке. Переключение
после устойчивого превосходства. Тиры не трогать.

## K. Пер-модельный предиктор и квотный порог

### K.1. Предиктор

Для каждой routable-модели — лёгкий регрессор на том же векторе,
предсказывающий `P(success | query, model)`. Обучается на логах B.
Выбор — argmax при ограничениях (модальность, инструменты, контекст,
остаток квоты, circuit breaker).

Тиры — фолбэк для новых моделей без статистики.

### K.2. Локальное против облачного — порог, а не сравнение

```
if P(success | query, local_resident) > threshold:
    route_local()
else:
    route_cloud()
```

`threshold` плавающий, привязанный к остатку квот:

- сразу после сброса окна — низкий, охотно уходим в облако;
- к концу окна — растёт;
- квота исчерпана — 1.0, только локальная.

Формула в конфиг; стартовый вариант — линейно от `quota_remaining_pct` с
поправкой на `quota_window_reset_in_s`. Текущее значение показывается в
интерфейсе (Часть II, блок 3).

## L. Режим ансамбля

**Последним и только если H показал запас между `p_best` и `1 - beta`.**

### L.1. Проверяемые задачи — self-consistency

Код, математика, извлечение структурированных данных.

- Веер по провайдерам **не применять**.
- Одна лучшая доступная модель, N сэмплов (3–5), ненулевая температура.
- Отбор исполнением или большинством по нормализованному ответу.
- Расход: один слот лимита вместо N.

### L.2. Непроверяемые задачи — fan-out

- Максимум 3 пропозера, обязательно **разных семейств**.
- Отбор — по матрице корреляции ошибок из H, **не по рейтингу**.
- Агрегатор строго сильнее пропозеров. Локальная резидентная не годится —
  её роль судья и фолбэк.
- **Таймаут обязателен.** Собирать вернувшееся за `fanout_timeout_ms`;
  минимум 2 ответа, иначе отдать единственный.
- Реализовать поверх починенного hedge-пути (F).

### L.3. Триггер

1. **Эскалация постфактум** (основной режим): локальные ступени → облако →
   проверки → при провале веер.
2. **Предиктивный**: `risk` выше порога → веер сразу.

Конфиг: `ensemble.enabled`, `ensemble.risk_threshold`,
`ensemble.max_proposers`, `ensemble.fanout_timeout_ms`,
`ensemble.min_quota_pct`.

## 2.1. Dashboard — блоки сверху вниз

Порядок: чем выше, тем чаще смотрят и тем быстрее надо реагировать.

### Блок 1 — полоса состояния (одна строка, всегда видна)

Слева: число запросов, доля эскалаций.
Справа: самое срочное. `groq: квота кончится в 12:00, за 2 ч до сброса`.
Если спокойно — «всё в норме».

Это замена вкладки Alerts: строка либо молчит, либо кричит.

Сюда же — молчаливый индикатор `outcome_coverage`: показывается **только**
когда падает ниже порога. Формально это метрика из Setup, но если она
просядет, а узнаешь через месяц, обучать будет не на чем.

### Блок 2 — воронка каскада

```
IN 143 → CACHE 12 · 8% → LOCAL 98 · 69% → CLOUD 27 · 19%
       → ESCALATED 6 · 4.2% → FAILED 0
```

Справа крупно — `local_hit_rate 77%`. Одно число, отвечающее на вопрос
«работает ли вообще вся конструкция». Клик по стадии → трейс с фильтром.

**Стадии называются стадиями.** В текущем трейсе встречается `mini` там,
где должна быть стадия — исправить на `local` / `cloud/<model>`.

### Блок 3 — квоты строками, не карточками

Одна строка на провайдера, сортировка по близости к исчерпанию:

```
groq        ████████░░  72%   38/min   binding: requests   → 12:00 (сброс 14:00)  ⚠
openrouter  █████░░░░░  47%   19/min   binding: tokens     → хватит до сброса
cerebras    ███░░░░░░░  34%   14/min   binding: tokens     → хватит до сброса
mistral     ██░░░░░░░░  24%    7/min   binding: requests   → хватит до сброса
```

Детали (оба окна, точные числа, обратный отсчёт) — по клику на строку.

**`binding` обязателен:** какой лимит упрётся первым, запросы или токены.
Прогноз считается по нему.

**Требование к прогнозу:** он обязан вычисляться из тех же чисел, что
показаны в строке, и покрываться тестом на согласованность. В мокапе была
несостыковка — сброс в 14:00, прогноз исчерпания 14:20, подпись «до
сброса», а по скорости сжигания выходило 12:00. Четыре разных ответа.
Главная метрика страницы не должна тихо врать.

Справа от блока — текущий порог `local↔cloud 0.61 ↑`, как прямое
следствие состояния квот.

### Блок 4 — латентность и эскалации (в ряд)

Слева: local P50/P95, cloud P50/P95 — четыре числа, каждое подписано,
плюс спарклайн P95 двумя линиями за час.
Справа: причины эскалаций барами, кликабельные в трейс. Нули здесь
информативны (`timeout: 0` — это факт), в отличие от нулей выключенных
подсистем.

### Блок 5 — модели (свёрнуто до топ-5)

| Модель | Бэкенд | Thinking | Первичных | Эскалац. | Успех | P50 | P95 | Токены |

- **Бэкенд** отдельной колонкой (`mlx` / `ollama` / `cloud`) — без него
  сравнение локальных и облачных цифр вводит в заблуждение.
- **Первичных / эскалационных** разделить: модель, которую зовут только
  при провале предыдущей, по определению имеет худшую статистику.
- **Локальные строки обязательны.** Сейчас их нет, хотя через них идёт
  69% трафика.
- Роли (`A1` / `A2` / `F1`) расшифровать или убрать.
- Кнопка «показать все» → полный список с фильтрами.

### Блок 6 — живой трейс (последние 15 строк)

```
10:47:14  req_81c5  cache miss → local → degenerate → cloud/compound → accepted   1.98 s
```

Клик разворачивает попытки из `attempt_log`: стадия и `routing_source`,
модель, бэкенд, `thinking_mode`, TTFT и полное время, токены (+
`reasoning_tokens`), результат проверок, `outcome` и его источник. Плюс
решение роутера на входе: метки L0, предсказание L1 (даже если не
исполнялось), остаток квоты на момент решения.

Exploration-строки помечать явно и показывать обе ветки рядом — это
единственное место, где сравнение видно вживую.

### Чего на Dashboard нет

Сэкономленных долларов, `billed responses`, счётчиков выключенных
подсистем, конфигов, здоровья данных.

## 2.2. Setup — всё редкое

### Подсистемы

Список статусов, не метрик. Колонка «эффект» обязательна: `off` без
объяснения последствий бесполезен.

| Подсистема | Статус | Эффект |
|---|---|---|
| Эмбеддер | not loaded | блокирует L1 и semantic cache |
| Семантический кэш | off | — |
| Точный кэш | on | hit rate 8% |
| Сжатие контекста | off | — |
| Hedge | on, 0 из 196 | проверить порог |
| Идемпотентность | on, 0 replays | — |
| Local-first | on | см. Dashboard |
| Ensemble | off | ждёт замера β |

Строка про hedge с 0 срабатываний из 196 должна выглядеть как проблема, а
не как метрика.

### Локальные движки и память

Какие бэкенды подняты, какие модели резидентны, **потребление памяти
против лимита** (на 32 ГБ это первое, что надо видеть), время последнего
рестарта, состояние прогрева MLX.

### Ключи и провайдеры

Кто без ключа или с невалидным. Проверить согласованность с probe: на
мокапе `nvidia — missing key` соседствовал с healthy-моделями nvidia.
Расхождение означает, что состояние ключей и probe берутся из разных мест.

### Здоровье данных

- `outcome_coverage` с разбивкой по источнику; отдельно доля «слабых pass».
- Объём `attempt_log`, прирост за сутки, распределение по `task_type`,
  модальности, бэкенду.
- Записей на каждую модель — модели с единицами наблюдений не получат
  предиктора.
- Доля exploration, текущая и целевая; сколько моделей получило
  статистику благодаря ей; `routing_regret`.
- Состояние L1: обучена или нет, дата, размер выборки, качество против L0,
  режим (параллельно / исполняется).

### Замер β

`p_best`, `beta`, потолок `1 - beta`, дата прогона и вывод: имеет ли смысл
ансамбль. Одна строка, определяющая целую фазу.

### Pricing

Сэкономленное, сравнение с платными baseline, суммарные токены. Baseline
(GPT-4o-mini / Claude 3.5 Sonnet / o1) устарел — обновить, вынести в
конфиг, добавить дату цен. Это витрина, а не операционная метрика.

## 2.3. Замечания по визуальному стилю

Текущее направление верное: тёплый фон вместо чистого белого, приглушённые
акценты, моноширинный только на значениях. Что поправить:

- **Разрядка (letter-spacing) стоит почти везде** — на заголовках,
  подписях, мелких метках, статусах. Когда разрядкой набрано всё, она
  ничего не выделяет. Оставить на одном уровне — заголовки секций.
- **Слишком много кеглей** (31 / 30 / 22 / 14 / 13 / 12 / 11 / 10).
  Хватит пяти-шести.
- **Заголовок страницы конкурирует с главным числом** (31px против 30px).
  Заголовок читают один раз, число — постоянно. Заголовок уронить до
  20–22.
- **Два оттенка панелей неразличимы** (#ffffff и #fcfcfb). Либо заметная
  разница, либо один.
- **Всё в рамках** — ничто не отступает на второй план. Второстепенные
  блоки давать без обводки, отбивая пространством.

## M. Антипаттерны — не делать

**Бэкенд:**
- Подключать MTP-воркер — на 32 ГБ он замедляет, а не ускоряет.
- Переносить `set_memory_limit(2**35)` и `set_cache_limit(2**33)` из CLI —
  это вся память машины, рассчитано на конфигурацию без соседей.
- Держать Gemma 4 12B резидентно рядом с 27B — не помещается.
- Фиксировать `enable_thinking: false` на уровне сервера — убивает
  ступень D.1.3.
- Использовать устаревший `python -m mlx_lm.server`.
- Запускать демон через `uv run` вместо фиксированного venv.
- Забыть `mkdir -p ~/logs` перед загрузкой LaunchAgent.
- Отдавать запросы в MLX до завершения прогрева.
- Держать 9 локальных моделей маршрутизируемыми.
- Сравнивать бэкенды на коротких промптах.

**Данные и обучение:**
- Обучать голову на метках L0.
- Логировать одну строку на запрос вместо строки на попытку.
- Исполнять решения роутера в 100% случаев.
- Спрашивать у модели её собственную уверенность.
- Строить ансамбль до замера β.
- Ставить несколько энкодеров в основной путь.

**Маршрутизация:**
- Ставить локальную модель в fan-out.
- Гонять thinking-ступень на задачах, где рассуждение не помогает.
- Тратить облачную квоту на служебные вызовы.
- Разворачивать веер без таймаута.
- Писать параллельные вызовы с нуля, не разобравшись с hedge.
- Включать compression и semantic cache одним изменением.

**Интерфейс:**
- Плодить вкладки по темам вместо частоты использования.
- Показывать прогноз исчерпания, не выводимый из чисел в той же строке.
- Держать нулевые метрики выключенных подсистем на Dashboard.
- Ставить имя модели там, где должна быть стадия каскада.
- Подписывать P50 как «average».
